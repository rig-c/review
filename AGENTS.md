# review

A standalone human inspection and structured feedback app. Read README.md, docs/REVIEW_PACKAGE.md and docs/DESIGN.md before changing the delivery contract.

- Work here; do not edit rigc, parts or play core repositories as part of review changes.
- Keep supplied source assets and compiled models immutable. The producer writes motion in scratch; review never authors keys and never writes the package's motion.json: motion edits (idle tracks, blink, retarget flags and pose maps) are data the installed producer builds into a scratch build, and a labelled preview before Apply is never recorded or submitted. Store feedback separately, bound to package identity, revision and actual input hash. Opening a package never approves it.
- All package assets must remain inside the package directory, with literal portable paths and no symlink escape. Never execute a manifest command or fetch a remote asset on its behalf.
- Playback uses the published `@rig-c/play` API. A loaded model is not proof of the upstream compiler's gate. State source provenance and missing capabilities honestly.
- View, Rig, Playback and Feedback are sections of one inspection workspace. Key authoring is outside this app; motion changes reach the producer as data (config patch, pose map, flags) and come back as a scratch build. Do not label placeholders as working editing tools.
- The chest-region editor and Edit Mesh are a precision instrument for detail that cannot be said in words: the loop is "point → rebuild → watch → repeat → submit" (issue #99). Review builds no mesh itself. Apply · Rebuild runs the installed producer (`rig-parts`, found in the nearest `node_modules` from the package, then from review's working directory; refused by name when absent, never installed by review) as a child process on the user's own designation, into a scratch build under the review state directory, never into the inspected package, and reloads that build in place. A target the producer has no operation for refuses by name. The last applied inputs and the producer's line go into the draft and the submitted feedback, so the AI receiving the review can rebuild exactly that state.
- Require same-origin JSON mutations, a loopback-only server, bounded payloads and no arbitrary filesystem endpoint.
- Run focused tests for path/state boundaries. Use the global nova-run skill for full test/build/typecheck bundles.
- README is for deciding and getting a first result: what the package is, install, one first run with output, one line per panel or command with a link, and links. A feature PR adds at most one line. Put flag lists, refusal catalogues, dated or machine-specific figures, version history and development details in reference docs; license text stays behind a pointer. Move text without losing it, retain inbound heading stubs, and repoint content tests. Ship linked reference docs in package.json `files`, or use absolute GitHub URLs. Run `bun run check:readme` and `bun test tests/readme.test.ts`: the fixed 800-word cap (#224: 701 post-cut words + 10%, rounded up to 50, below the earlier 2,500 limit), heading allowlist and dated-phrase/table-date refusals are proved by named planted mutants. (Naru, 2026-10-30)
- Use Conventional Commits in English. Agent-authored commits and final squash commits carry the authoring agent's own `Co-Authored-By` trailer; this file names no single agent. Parent agent handles Git landing; execution agents do not run Git.
